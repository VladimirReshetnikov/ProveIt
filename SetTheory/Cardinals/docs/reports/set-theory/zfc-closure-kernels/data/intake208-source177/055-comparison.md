# Candidate recommendation after inspecting the incoming proposals

Snapshot: `53269bcab1efc0f82d3022645bd7cf0c22d84959`.

## Three questions should be separated

1. **What best shortens the existing complete proof?** Keep the literal primary
   K215, preserve its public theorem, and refactor the shared proof layers.
   The complete logical calibration, strong compiler, primitive runtime,
   exact startup and table binding already have compiled Lean/Rocq endpoints.
   Changing the machine is unnecessary for this objective.
2. **Which alternative needs the shortest additional correctness proof?**
   Prefer the M124/FM215 predecessor-selector family, or CM215 when its
   already compiled dense/Core bridge is decisive. M124/FM need two immediate
   incoming-edge invariants and two three-step replacements. This supports
   a short relative proof importing the old endpoint. Its entire inherited
   dependency closure has not thereby disappeared.
3. **Which alternative has the cleanest independent scheduler argument?**
   ZC215 is the strongest candidate. Exact exhaustive enumeration and the
   NIP-to-DROP injection replace arbitrary-tail credit arithmetic. It keeps
   the original four command contracts, unlike direct-transfer candidates.
   This is an architecture judgement, not a measured claim that ZC215's
   complete endpoint has fewer source lines or compiles faster.

## M124 and FM215 are one closely related proof family

An exact parser comparison of all 430 native rows finds just one difference:

| Row | M124 | FM215 |
|---|---|---|
| `127 / 1` | `1 R 59` | `1 R 109` |

The rows `59 / 0` and `109 / 0` are both `0 R 62`. Both variants merge old
logical roles 124 and 127 at new control 124, use physical 127 as origin
selector, and preserve 215 working states. Their common changes relative
to the primary are `110/0`, `124/0`, `127/0`, plus the above provider choice.
The old incoming rows force predecessor bit 1 at role124 and bit0 at
role127. Thus the same proof schema covers both provider choices.

The original M124 note explicitly says that providers 109 or125 can replace
59. Consequently FM215's graph distinction does not justify treating its
underlying mathematical idea as independent from that documented provider
family. This observation concerns the packets and supplied proof family,
not global priority.

Native SHA-256:

- M124: `8e0ccb4b631c4e4c1c02c4b52a6fe382984e67557dd1dcd949065479e38d07b9`.
- FM215: `3ece1233f11d33375425221c5bcedba941e073763912990eabf321197772dce5`.

Both deliveries report the identical complete calibrated tape after 95,840
steps versus primary K215's 95,714; exactly 63 old steps stretch from one
to three. This comparison did not rerun that finite startup. A generic
finite checker for the two-invariant family is a natural further proof
simplification, while preserving the exact tables and semantics.

| context returns | History-sensitive returns can improve allocation but require more contextual invariants. |

| conditional marker CM215 | Very short relative all-tape transport already delivered, with one more origin case than M124/FM215; some incoming packets already bind it to actual dense semantics. |

All these candidates still require the inherited numerical-calculus/ZFC
calibration. A well-formed-formula invariant must not be added unless the
machine genuinely enforces it: raw aliases and nondecodable numbers are
part of the existing soundness/completeness contracts.

## State-count consequence

No part of the concrete credit proof removes a physical state. It gives a
useful semantic freedom: future AX changes need not preserve a ten-head
credit contribution for scheduler safety. They still must preserve logical
soundness and strong completeness, and have an exact binary allocation.
Likewise the M124/FM selector uses the role freed by the fold, so it saves
zero physical states. A 214-state claim needs an additional independently
validated way to implement that selector using existing controls, or a
more global source/encoding transformation. No such construction follows
from the proofs or comparisons in this directory.
