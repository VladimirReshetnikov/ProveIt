# First four-port byte-recipe join attempt

The preflight `prepare.py` combined the accepted beta, K, MC and shifted-MF
author objects into a fresh 630-file selected provider root. It checked all
four producer source/object/log hashes and current direct dependency and
companion guards, revalidated the prior K, MC and MF provider manifests and
recorded provider paths, compared every overlapping selected file, rejected
any differing shared hash, and suppressed no foreign companions. The
complete manifest and sampled receipt hashes are retained in
`observations/prepare-attempt01`.

The bounded Lean run `observations/attempt01` **failed** with kernel
excessive-memory consumption while checking `decode_ports` directly on the
concrete tuple. No output object was produced; the error-recovery axiom
report mentioning `decode_ports` is not a proof. Its exact source, log,
direct guards and terminal receipt are retained. The 630-file selected union,
all four checked producer sources/objects/logs, prior recorded provider paths
and direct dependency guards were unchanged at the recorded postchecks.

The intended assertion identifies the four decoded **Lean** byte recipes
with the fixed symbolic natural tuple `[beta, K, MC, beta+high]`; no such
four-port theorem is established here. In particular this attempt proves no
file/gzip identity, parent-to-supplement provenance, PDF binding or iPRA
endpoint. A separate retry should prove the tuple-mapping fact over abstract
lists first, then specialize without normalizing the large concrete recipes.
These checks are author-side and point-in-time, with package/transitive/
dynamic ancestry inherited; they are not a paired replay or full audit.
