capture for `Trace75FixedCongruence` and `DirectBFSBandCarry`, plus the
coherent BFS replay receipt. The historical trace75 root includes both
`ModelRatioBounds` and `ArithmeticNegativeNorms` objects that differ from
the fresh BFS union. The observed reverse dependency cone has 18 project

`plan.py` checks each of these 14 current source files against its accepted
producer snapshot, source pin, output hash and log hashes. It compares all
208 selected trace75 project ancestors with the current BFS union, including
all companion presence/hashes: 152 agree, 10 primary objects differ, and
46 are absent. Eight differing names are deliberately rebuilt generic
helpers; the two historical project differences are the seed modules above.
The 46-object BFS BandCarry subtree has no conflicting or absent name in
the trace75 classification. Full records and ordered direct stage imports
are in `observations/plan-attempt01/result.json`, SHA-256
`053d235687f3024ebb10df6d660d0651797b56096e885f9d88fcb2692138217d`.

This is a plan, not a replay or proof that a union is ready to build. A
future guarded runner must construct a fresh non-clobbering union, preserve
the correct trace75 versions of the eight distinct generic helpers, select
the fresh BFS versions of the two seed modules, verify companions and all
selected input/source hashes before and after each relevant step, check
topological dependencies and any other selected-module overlaps, capture
each command/diagnostic and actual outer exit, and be independently reviewed
before execution. A completed replay would still require an explicit
serialized closure and source/provenance audit. The scan does not establish
full historical trace75 source-to-object or outside/package/dynamic ancestry.
