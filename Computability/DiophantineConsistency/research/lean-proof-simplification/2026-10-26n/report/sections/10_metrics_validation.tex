\subsection{The validation sequence}

\begin{enumerate}
\item \textbf{Use the actual pinned project.} Work in a complete disposable
checkout at the review pin, with
\code{leanprover/lean4:v4.32.0} and the locked mathlib dependencies. The
selected source snapshot is evidence, not a standalone Lake workspace.
\item \textbf{Compile the independent candidates first.} Record Lean/Lake
versions and command output. Check A1's total-decoder dependency, A2's
recursive option simplification, C1's library signature and C2's numeric
normal forms before editing production proofs.
\item \textbf{Test the actual edit shape.} Apply exact patches only in the
throwaway checkout. For C3, relocate the helper and retain required aliases;
for C4, reorder declarations. Compiling a standalone file that imports later
modules does not validate these production import-order changes.
\item \textbf{Compare public statements and axioms.} Preserve old theorem
names, hypotheses and conclusions; inspect every expected endpoint's
\code{#print axioms} result. A missing or empty audit log is not a pass.
Compare dependency sets with the original declarations rather than merely
searching for one forbidden string.
\item \textbf{Replay affected consumers.} Rebuild the annotated checker,
current word/cell/occupation modules, Wang boundary/seam consumers and
bounded-quantification Checks modules as applicable. Only then measure
elaboration costs with identical options and a recorded warm/cold policy.
\end{enumerate}

\textbf{Available evidence.} Byte verification, static declaration checks,
patch dry runs and finite arithmetic smoke checks help catch packaging or
specification mistakes. None proves that Lean accepts a candidate. The
supporting \pathcode{validation/} tools exist to make future replay
reproducible; they are not another novelty claim or a substitute for it.
