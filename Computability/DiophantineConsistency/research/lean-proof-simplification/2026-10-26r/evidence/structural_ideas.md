## The strongest surviving candidate

Define one small syntax describing each rule's output code and list of premise codes. Interpret this syntax numerically and compile it into the existing supplied primitive-recursive program constructors. The same 17 entries then define both the numerical specification and executable program, with one structural compilation theorem.

This is distinct from earlier finite-tag-dispatch advice. `ArithmeticFiniteSwitch.program` already handles dispatch. The remaining duplication is inside the branch bodies: one written copy says what the output/premise codes mean, and another writes the supplied PR program for those very formulas. This also differs from automating the existing `fin_cases; rfl` proofs, which an earlier packet correctly regarded as too short to justify metaprogramming.

### Mathematical statement

Let `T` be syntax freely generated by ten coordinate fields, natural literals, and the existing atom/fork/list-cons coding operations. Let `eval_C` interpret the operations in the numerical coding algebra. A supplied-program backend gives operations on actual program data `Code`, evaluation `run`, and the five equations that these operations implement the numerical operations.

Structural induction proves

`run (compile t) raw = eval_C (coordinates raw) t`

for **every raw input**. No well-formedness condition on the coordinate packet is used. Applying the same theorem to the output term and the term encoding the premise list establishes the complete schedule implementation. The canonical-coordinate facts remain independent: they show that the numerical schedule for a valid coordinate packet agrees with the original `Rule.output` and `Rule.premises`.

### Small language sufficient for the actual 17 rules

- `field f`, with fields context, shifted, a, b, c, instI, instJ, shiftC, i, j.
- `literal n`.
- `atom t`.
- `fork t u`.
- `cons t u` for numeric list coding.

`binary tag a b`, `unary tag a`, `variableNode tag i j`, and `bottom` are transparent syntactic abbreviations. No general-purpose metaprogram is required. The standalone prototype includes all actual 17 schedules and the same invalid-tag zero/empty default.

### Honest payoff assessment

This is primarily a maintenance improvement, with proof simplification emerging because the correspondence of numeric and supplied-program branches is established once by syntax induction. It removes duplicated branch semantics, which survive earlier dispatch and scanner refactors. It is **not** yet a measured line reduction or speed improvement. Generic syntax/backend infrastructure can increase source size for the first client, and the existing dependent `R` type already catches many semantic mismatches. Adopt it if the project expects to maintain or extend several such tables, or if the full backend can be made very small; otherwise the current four compact definitions are reasonable.

The benefit should be measured as independent copies of each semantic branch (two per output/premise today, one under this scheme), changes needed when a branch changes, and actual net LOC/compile time after integration. Do not count generic framework lines as free.
