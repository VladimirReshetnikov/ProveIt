# P72 and sign33 provider comparison

This is a source-only, point-in-time comparison, not a Lean run or a claim that either already checked historical theorem is invalid. An initial verbal report mistakenly compared P72Aux's `ArithmeticPellHalfIndex` dependency with the different `ArithmeticPellFirstIndex` module. The first draft of this checker also tried to look up that wrong module in P72Aux's dependency map and stopped with a `KeyError`; it made no successful mismatch observation. The corrected checker explicitly compares HalfIndex against HalfIndex: its recorded P72Aux object hash `6142ab8eaac6e281c3372817a6f1a8cbc14704717d4f5479c28603c754c3a4d7` matches the live object and the sign33 survey. The distinct FirstIndex hash `20d3769d891a42810c1985203768b122bf936884494d2829415e3140d6deb9c2` was not a valid comparison.

The corrected checker verifies the retained successful P72 extension progress and P72Aux row, all 300 direct-guard slots and recorded direct dependency paths/hashes for P72Root, P72Main and P72Aux, and compares all currently present matching paths between the P72 lib tree and the retained sign33 inner/V provider survey. Among 1,007 overlapping files, exactly one differs: `DiophantineConsistency/ModelDifferenceRing.olean` has SHA-256 `cf2b32cb1e4777b7cff73c34ed7334a105f705912fa987e9f7f9a316fef192f0` in the sign33 survey and `e52ed546fa3f94d9c3b823ad19286c4c906359efa26c1d67543e9dbfc0f2ecf0` in the P72 lib tree. This detects a byte mismatch and is insufficient to conclude semantic incompatibility, but the P72Aux object is not injected into the sign33 overlay without a coherent provider bridge. It does not audit all transitive or dynamic dependencies and observes mutable paths only at check time.

Run `python3 -I -S -B check.py`. Checker SHA-256 `65699f5fe006953810b763f0d35e47e9bea02faa2e82d33e92895838b2af3462`, result `811dcad57d828cff5307aaafc9769dd7e017771e70ecee4278f0e762112729b9`; actual corrected checker session 2453 returned numeric exit 0. No Lean run.
