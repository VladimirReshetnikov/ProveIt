# Newly merged thirteen-variable endpoint: declared closure and successor plan

The newly merged `ModelThirteenCarrier.lean` declares a model-level `complete`, a two-way `sameNoZero69`, a `bridge69`, and native, standard and equality-only iPRA equivalence theorems. These are source declarations, not yet validated endpoints. The newly merged `ArithmeticThirteenOuter.lean` and `ArithmeticThirteenSeed.lean` overlap earlier separately audited work. None was an input to the previously replayed 70-module parent, 24-module window suffix, or conditional 69-converse packet.

## Source-declared closure and actual object comparison

[`survey.py`](survey.py) recursively follows declared source imports from `DiophantineConsistency.ModelThirteenCarrier`, using the independently audited 70-source snapshot as a boundary. The anchor is commit `ca2b5071e3c647e4bf3039ac52e4308a179dcfa6`. Its [source manifest](source-manifest.json) records 1,081 additional source modules, 41 direct boundary modules, and 99 external direct imports. Expanding the reachable portion of the 70-source boundary gives **1,145 selected project modules**, including 64 of those 70 sources. The initial survey attempt, preserved as `failed-comment-scan.py`, failed because it treated a line inside a block comment as an import. The corrected scanner recognizes nested block comments, line comments and strings; no modifier-style import lines were found in the surveyed source files. This remains a source-declared survey, not Lean's `--deps` output.

[`compare_historical.py`](compare_historical.py) compares the selected sources against the independently audited historical 1,210-module paired parent. Of the 1,145 selected modules, **1,096 overlap**, **49 are new**, and **15 overlapping source files changed**. No overlapping module's declared import list changed. The complete [comparison](historical-comparison.json) lists all changed and new modules and the reverse closure. The changed/new source seeds have a declared reverse closure of **338 modules**; **807** selected historical sources lie outside it. Both historical sides' 1,210 retained `.olean` files were rehashed: none was missing, symlinked, or different from its recorded hash, and no sibling object hash differed. This is an actual object-byte check, not proof that any historical object is source-current with respect to changed dependencies.

The separate [current-provider object comparison](provider-object-comparison.json) records 104 actual overlapping project objects per side. Six differ in bytes between our recently audited model-view overlay and the historical pair: `NaturalExpression`, `ArithmeticBinomLegendre`, `ArithmeticBinaryCarry`, `ArithmeticCyclicWord`, `ArithmeticWindowCarry`, and `BusyBeaver.ZFC.KZip`. Five of these have unchanged selected source text. Therefore the prospective successor must not silently mix the current model-view overlay with historical seeds. Reuse must retain the historical seed closure and recorded dependency objects; the 338 dirty modules must be rebuilt against it in order.

## Candidate bounded successor

[`frontier_plan.py`](frontier_plan.py) produces the [topological frontier](frontier-plan.json). It checks that every selected project dependency precedes its client, no reusable seed depends on a dirty module, each clean seed has the same historical and current source hash, and each reused object matches its recorded historical hash. It checks recorded direct import kinds, paths and hashes, plus 9,080 unique direct-input and reused-output companion paths on **each** side. It also records current direct package/toolchain object and companion guards for all 27 external imports of rebuild modules, including implicit `Init`. The inventories are point-in-time checks. A successor builder must preserve sibling isolation, pin its source snapshot and inputs, recheck all guards before and after each relevant compilation, compare actual direct imports with `lean --deps`, fail closed on compiler errors/admissions or drift, and be independently reviewed before launch. A separate independent review of this planning packet is also needed.

The frontier is a plausible **338-module** successor rather than an established minimal rebuild or completed build. The historical author logs took 2,381.9 seconds for the 289 frontier modules that existed in that parent, roughly 79 minutes for two such sequential passes before the 49 new modules, dependency queries, auditing and overhead. That is only a rough historical baseline, not a runtime bound; new endpoint modules could be substantially slower or exceed resource limits. Resource limits must be monitored and reported as sampled checks, not guaranteed quotas or disk reservations.

After the endpoint build, rebuild the separately pinned `Thirteen69Nodes.lean` and `Thirteen69Cuts.lean` against that **same** successor, then compile [`Model69EndpointBindingDraft.lean`](Model69EndpointBindingDraft.lean). The draft proposes a ring-evaluation equality between `ModelThirteenCarrier.expressionAt69` and the independently audited 69-node literal, then an equality of their shifted internal-zero predicates. It has **not** been compiled. It is a semantic binding, not literal AST identity or a Lean theorem about the external JSON row count. Pin and audit the original 69-row source and its exact 2011 ports again when using it.

The successor must print and inspect axioms for `complete`, `sameNoZero69`, `bridge69`, `native_equivalence69`, `standard_equivalence69`, `reference_equivalence69`, and both proposed binding lemmas; reject `sorryAx` and unexpected admissions, and distinguish Lean metatheory axioms from object-theory axioms. Check the exact endpoint statements and their Foundation consistency predicate, rather than assuming that a theorem name establishes the intended external consistency equivalence. Neither this plan nor the new source declarations establish the endpoint.

The historical Foundation provider's outer wrapper exit remains unobserved; package-transitive and dynamic ancestry, mutations between observations, and the existing prefix/window incomplete printed axiom inventories remain outside these checks. A completed source-current Lean build and independent artifact audit are still required.
