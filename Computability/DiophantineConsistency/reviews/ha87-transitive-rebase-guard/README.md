# Transitive project-closure guard for full-source rebases

This is a proposed, separate full-source driver. It preserves earlier driver and build evidence. Before reusing a module, it traces the prior record to its actual successful compiler invocation, then compares the original compiler environment and new overlay throughout the source-declared project import closure: project/package classification, direct import lists, original verified project objects and their current object hashes. It also compares direct external object and companion hashes. It records the transitive fingerprint and original compiler-state hash, rechecks consulted objects at final audit, and rejects a resumed reused row that lacks or no longer matches that evidence. Mismatches cause recompilation rather than reuse.

The synthetic `tests.py` executes the actual guard function from the driver and verifies that an identical closure is accepted, while a changed transitive object despite an unchanged immediate object, a changed external companion, changed import edges, and a tampered original object are rejected. `tests.log` records the result. The initial code-generation attempt failed before creating a driver due to a patch-script substring mismatch; no proof/build input was produced by that attempt.

These checks concern source-declared project imports and direct external objects/companions. They do not establish a complete audit of dynamic imports or transitive package objects/sources. The driver has passed Python syntax and synthetic guard tests only; it has not yet performed an end-to-end Lean build or independent replay. Preserve all earlier build results with their original weaker rebase qualification.

The original transitive environment is reconstructed from surviving origin-overlay objects and verified records. Those objects were not all independently hashed immediately before the original compilation, so this check cannot rule out unrecorded mutation during that original compile. A fully fresh build is stronger. Transitive manifests are kept as separate per-module files to avoid repeatedly rewriting a large state file; their hashes are rechecked on resume and final audit.
