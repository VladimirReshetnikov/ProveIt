# Foundation provider recovery: input snapshot

The historical `/tmp/pra14-full-transitive-2x6o__to/package-lib` overlay
contains 140 Foundation object links. At the time of the recovery survey,
135 object links and their associated companions targeted the now-missing
`/home/codex/src/Proofs/.lake/build/lib/lean` tree. The overlay itself has not
been changed. Its old receipts remain historical evidence and are not a
currently usable provider.

[`input-manifest.json`](input-manifest.json) records those 140 module names
and SHA-256 digests of all 477 files in a fresh `git archive` of the exact
Foundation gitlink commit `32e1a0956a8622fad067328ca1959729a7634428`. It also
records the Lake configuration, manifest, toolchain and Lean executable
digests, and the inherited mathlib checkout revision. The temporary isolated
build root is `/tmp/ipra-foundation-rebuild-DqHJmJJe`. Its Lake configuration
declares a `Foundation` library at `lib/FormalizedFormalLogic-Foundation`,
requires mathlib `v4.32.0`, and uses the existing package build directories.
[`build_all.py`](build_all.py) verifies the pinned inputs, attempts the 140
named targets in a fresh root with no prior build, guards the explicitly
imported external objects and companions before and after, and guards against
foreign Foundation objects and earlier external-object shadows in the Lake
search path. It sanitizes inherited Lean and dynamic-library search environment
variables, monitors free space, and records its actual outcome. A success creates a new overlay with
fresh Foundation objects and inherited non-Foundation packages; it does not
modify the historical provider. The guard is not an authentication of the
external packages' transitive or dynamically loaded dependencies, and its
before-and-after checks cannot exclude mutation followed by restoration.

A first targeted Lake build of `Foundation.FirstOrder.Arithmetic.IOpen.Basic`
and its dependencies was started in that root. This input record is **not a
successful build receipt**. A new build must record its actual exit, outputs,
dependency provenance, and compatibility with the existing project objects
before it can support a replay. In particular, a newly compiled Foundation
object is not presumed byte-identical to an unavailable historical object;
mathlib/package-transitive objects and dynamically loaded dependencies remain
inherited unless separately authenticated.

The [initial direct-hash comparison](initial-comparison.json), generated by
[`compare_historical.py`](compare_historical.py), checks the Foundation
dependencies recorded in the 848-module historical state. At that point one
of its 32 distinct direct Foundation objects had been rebuilt; that object's
hash differed from the recorded historical hash. This is a point-in-time
observation, not a diagnosis of the cause. Future comparisons and explicit
compatibility checks with inherited project objects are necessary before a new
provider can support proof-replay claims.

The separate root `/tmp/ipra-foundation-guarded-ieOVZs2r` was prepared with
the same source snapshot and configurations for a clean guarded build. A
preflight source-closure walk found 140 Foundation source modules and 43
declared external imports, corresponding to 430 present-or-absent companion
paths. That attempt was intentionally stopped after discovering that it did
not guard earlier search-path shadows. Its [failed receipt](guarded-attempt-termination.json)
and [terminal observation](guarded-attempt-observation.json) record Lake's
SIGTERM exit and the outer process's failure; no outputs are reused.

The independent fresh root `/tmp/ipra-foundation-guarded-v2-cjHUaJun` passed
preflight with 140 source modules, 43 declared external imports and 14,764
presence-or-absence guards, including all foreign Foundation companion paths
and external search-path shadows. The [guard tests](test_guards.py) reject
injected shadow objects, altered objects, new companions, foreign Foundation
objects or companions, and empty or relative search-path components.
Preflight success is not a successful build or a completed replay.

During the build, Lean's namespace-first module search was independently
identified as a distinction from simply taking the first existing module
object. The [live namespace inventory](live-namespace-observation.json),
generated by [`observe_namespaces.py`](observe_namespaces.py), records the
effective search path and all guarded inputs. At that instant each relevant
namespace (`Aesop`, `Foundation`, `Mathlib`) had exactly one provider, with
Foundation supplied by the fresh build root. This is a point-in-time survey,
not evidence of continuous namespace stability or dynamic-import tracing. A
post-build rerun exited zero and produced the identical inventory hash.

The v2 driver emitted `BUILT 140 Foundation targets` and its [receipt](v2-build-receipt.json) records
inner Lake exit zero, 140 named object hashes and 1,540 inventoried artifacts.
The polling wrapper did not retain the **outer** process exit-code field, so
the [terminal observation](v2-terminal-observation.json) explicitly records
that code as unknown; the closed session cannot be polled again. Independent
verification of the receipt, artifacts and project coverage is pending. The
remaining package-transitive, dynamic and point-in-time guard limitations
continue to apply.
