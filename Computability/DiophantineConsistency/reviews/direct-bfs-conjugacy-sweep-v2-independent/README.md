# Independent review of direct-BFS conjugacy sweep v2

This review concerns the frozen `research/direct-bfs-lean-conjugacy-coverage-prototype` v2 generator, 59 chunks, bounded-map manifest, runner, and completed endpoint pilots 03 and 04. It does **not** report a completed 59-stage sweep, re-run Lean, establish full source/object ancestry, or prove an aggregate Lean conjugacy theorem, iPRA result, or equivalence for the PDF equation.

`check.py` is an independent external Python check; `check-output.txt` is its observed output. It regenerates all sources and the manifest in an isolated temporary directory, compares every byte, reconstructs all finite maps and the two source row lists, and checks the pilot receipts and their output files. Run from any directory with `python3 -I -S -B reviews/direct-bfs-conjugacy-sweep-v2-independent/check.py` (the displayed relative path assumes the DiophantineConsistency directory). It requires the recorded ephemeral `/tmp` objects while they remain available. The checker is evidence about bytes and finite computations, not a kernel replay or a theorem.

The checker verifies source/log/object hashes, direct import selection, all required no-axiom output lines, successful exit, no warning/error/sorryAx in logs, sampled resource bounds, and the command flags. Pilot03 took 14.11 seconds and pilot04 30.18 seconds. Their object SHA-256 values were respectively `cd730f4e2a128afe1076e200b949e9057ccafb14061b174377f158907a146f3f` and `01d6d10d68934bb930423d7ff78b59d382fc86046bc49551c8ced3750356ce95`. Older pilot02 used a different runner and is not evidence for the v2 bounds.

The runner is sequential and refuses existing attempt and output paths. Before each stage it checks fewer than two live non-zombie processes named `lean`, at least 8 GiB available memory, and at least 4 GiB free on `/tmp`. It starts Lean with `-M3000 -j1 -DElab.async=false` and `LEAN_NUM_THREADS=1`, samples about every two seconds, and terminates the launched process if more than two Lean processes or less than 8 GiB is observed, or after approximately 100 seconds. These are sampled guards, with possible races between independent launchers; they are not a global lock, a continuous monitor, or a process-tree resource limit. The disk guard checks `/tmp`, so use an output root on that filesystem. The process-kill path targets the launched Lean process, not an independently tracked process group.

## Safe continuation

Use only one sweep runner at a time. Retain and monitor its actual live process handle; there is no automatic resume or inter-run lock. Do not start a replacement while that runner or its launched Lean child can still be live. After termination, inspect every terminal receipt and its matching source, logs, object, manifest, runner, and selected import; an unfinished stage or object alone is not an accepted result. Resume only the first unaccepted range with a **new** attempt and output root. A partial attempt may lack a final `result.json` even when some stages have accepted terminals. Aggregate disjoint accepted stage receipts explicitly before asserting all 59 ranges passed. No source currently imports the 59 resulting objects into one theorem merely because all stages succeeded.
