The previously held v2's two blocking defects are corrected in the separately frozen `research/ten-positive-80-coherent-rebuild/run-v3.py`, SHA `c262d844c28fe87954cfe06d14da359d08e4d88838cb32bce025f26b072269d5`. Static review found no blocker to **one coordinated guarded run** of that exact version. This review did not launch Lean or the rebuild; a successful result is not yet asserted.

`check.py` verifies the v3 digest, current exact fixed-client receipt and Lean executable pins, both 8-GiB launch/in-flight thresholds, and coded/uncoded error and warning plus `sorryAx` detection with independent positive/negative mutations. It checks that all 80 saved outside names presently first resolve under the runner's package/sysroot order to the captured paths and hashes. It calls the independent v2 plan check, which verifies all 127 current source hashes, direct source-import sets against captured headers, exact affected set and topological order, and the earlier independent drift reachability checks. The fixed client, 127-source plan, selected scan, header helper and Lean are pinned; the runner records and rechecks its own digest throughout the run.

V3 creates fresh observation and temporary output roots, a project union using symlinks to selected original companions, source snapshots, and then replaces only the fresh union's affected symlinks with newly compiled files. It records an atomic status snapshot and planned stage before each stage's preflight/launch. Direct source dependencies are resolved and their object/companion states checked around each stage; outside objects additionally have a current pre-run companion baseline. After stages and again after header-reading batches it checks all project union companions, outside object/companions, and all original and copied source hashes. It reads every rebuilt object's serialized header and compares its imports with the captured header, checks the four endpoint axiom-report lines, and rechecks input hashes. The outer runner is designed to return nonzero and mark the result FAILED on detected exceptions.

At launch it requires at least 8 GiB `MemAvailable`, fewer than two processes named `lean`, and at least 4 GiB free on `/tmp`; it invokes each Lean stage single-threaded with `-M3000 -j1 -DElab.async=false`, samples memory/process count at about two-second intervals, and terminates on an 8-GiB/count guard or timeout. Those are sampled guards, not an exclusive lock or process-tree resource guarantee. Coordinate one rebuild and avoid launching overlapping independent processes that race its preflight. A status snapshot can show a stage as `RETURNED` even after that stage's validations, because v3 does not rename it to `ACCEPTED`. Therefore do not infer a completed proof from a per-stage Lean exit or progress snapshot: require final `result.status=PASS`, **outer runner exit 0**, all 127 stage outputs and header batches, and independent verification of final selected imports and four endpoint axiom reports. Preserve the outer process result separately.

The runner currently stores an `initial-project.json` hash and uses the in-memory initial companion snapshot for final comparisons; it does not rehash that saved initial JSON at the end. Independent post-run audit should verify that saved JSON still hashes to the recorded digest before treating it as evidence. Likewise, the outside pre-run baseline describes current package bytes and companion states, not their historical producer lineage.

Even a successful 127-stage replay would resolve only that observed-drift project cone against the current selected package and the retained unrebuilt closure. It would not prove that all historical producer mismatches were discovered, that the previous differing Foundation package object equals the current one, or that package-transitive/dynamic ancestry, every unrebuilt source-object chain, or external JSON/PDF binding is authenticated. The 127-source plan is a captured-graph reconstruction, not a minimal or exhaustive provenance repair.
