# Independent review: sampled monitor and paired coordinator

This reviews original prototype `49377c7490` and corrected wrapper commit `0f09b04dec`. Independent monitor and paired toy suites actually exited 0 for both versions; the corrected runs were sessions 71253 and 22744. Their real subprocess cases include threshold stops, TERM-resistant descendants, coordinator interruption, stalled-monitor escalation, and an unverified identity left explicitly unconfirmed and cleaned up by the toy harness. The separate terminal observation binds all independent receipts and observed exits. Earlier producer tests that encountered ENOENT and ESRCH during procfs reaping, and the corrected test-only controls, remain recorded in the producer's `observations/` and README.

The original coordinator created its output inside a fake provider before rejecting an invalid snapshot pin; the original standalone monitor created its terminal inside a fake snapshot during a preflight stop. Both are reproduced using the archived original scripts and isolated fake roots. The corrected version checks snapshot and provider hashes and requires existing absolute provider root/overlay paths before output creation. Independent CLI controls verify rejection before writes for nested snapshot, provider and overlay outputs and a symlinked ancestor; the standalone monitor rejects an explicitly supplied protected snapshot root. The shared path-guard source is included in the coordinator's fixed-input hashes. Its checks remain point-in-time rather than protection against adversarial path replacement during writes; standalone callers must provide additional relevant protected roots.

A separate actual historical-builder control shows why optimized Python matters: with `PYTHONOPTIMIZE=1`, the unchanged assertion-based builder exited 0 and wrote `PASS` for an invalid fake provider and zero-module snapshot; the same fake inputs were rejected in ordinary mode before output. No Lean process or real provider was used. On the corrected wrapper, inherited `PYTHONOPTIMIZE=1` is rejected before output or builder launch, and the actual historical builder rejects that invalid snapshot when launched through the normal monitor. A successful fake builder observes `sys.flags.optimize == 0` and no `PYTHONOPTIMIZE`. An additional control sets `PYTHONOPTIMIZE` after importing the monitor and confirms its actual child interpreter still receives optimization disabled. Direct `python -O` launches of both wrappers are rejected. **Direct optimized invocation of the unchanged historical builder remains unsafe**; this review's result is limited to the reviewed wrapper invocation and its environment.

The thresholds remain sampled stops, not a hard quota or continuous reserve. A run may overshoot between samples; logical directory size excludes external writes, symlinks and filesystem overhead. The tested monitor does not confine escaped process groups, other writers or all temporary paths. PID/start-time checks before escalation are not atomic pidfd group operations; unknown identity remains unconfirmed, and a killed monitor cannot guarantee cleanup. The coordinator hashes its fixed inputs and records actual monitor, builder and comparator outcomes, but this review does not independently certify the builder, provider, source snapshot, comparator, or the artifacts of any future real build. No real project build was run in this review. All four independent review scripts fail closed in optimized Python mode.
