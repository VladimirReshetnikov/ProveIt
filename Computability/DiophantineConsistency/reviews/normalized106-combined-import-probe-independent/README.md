# Independent prelaunch review of the normalized106 combined-import probe

No Lean diagnostic was launched. The following assessment is conditional on the lifecycle limitations below and on separate operator coordination; it is not a gate or authorization to run.

Reviewed `runner.py` SHA-256 `ed5f3f1bf138e5ae3586dd9c7c1ae4b46b4f2065de7b9295e4c827b7cc935866` and `owned.py` SHA-256 `a41aee499bcef7b6ece79e1e7eae2b99210a70c1dafc1e54f2de55fbfc8d6201`. The hashes of both Lean client files, control driver, and three saved control receipts also match the probe README. On this machine, the author's documented `--selftest`, `--preflight`, and synthetic `test_owned.py` commands all independently returned exit 0; the preflight checked 210 direct object, companion and shadow paths. These tests start no Lean process.

The first client imports the current-base endpoint and the five stated extra Mathlib modules; the second imports Foundation's Matrix module plus the same extras. The two tests are intentionally different: failure of the second alone does not establish that the endpoint reaches Matrix. The endpoint object is checked against the saved producer record, its source and direct dependencies are rehashed, its log is checked, and the external candidates are compared with the pinned earlier inventory. The environment orders the current base before the recorded package path and removes several path/loader overrides. This authenticates the recorded direct paths only, not all transitive or dynamic loads, package source provenance, or a successful import.

The runner refuses an existing output directory, a detected other live Lean process, failed initial resource thresholds, or changed pinned inputs. It rechecks those inputs and its own hash before and after each case, records each actual reaped exit in a callback, and stops before case two if case one raises. `DIAGNOSTICS_FINISHED` means both processes terminated, not that either import succeeded. Each exit, log, saved state and outer runner exit need separate inspection. Memory and competing-process checks are sampled and can race; the resource limits are not kernel-enforced limits. Receipt-write failure, forced supervisor termination, escaped-session descendants and inaccessible procfs remain outside the advertised guarantee.

Two additional lifecycle limitations require explicit recognition:

1. `killpg` targets the leader's process group, not every process group in its session. A descendant that changes process group without leaving the session can survive both signals. The scan then normally notices it and the helper can wait beyond the nominal 120 seconds, potentially indefinitely; the timeout is not a hard wall.
2. A single `/proc` scan is not an atomic snapshot of a forking session. If a descendant forks during enumeration, changes in which PIDs are encountered can cause a live successor to be missed. Therefore a reported empty scan and `session_drained` receipt are conditional on the absence of that race; retaining an unreaped leader anchors its PID only until that leader is reaped. This is the enumeration issue described in `research/nine-variable-stop-rescan-assessment/README.md`, not a claim that the present direct Lean clients actually fork in that way.

The author was notified of both limitations. The existing synthetic tests cover ordinary completion, a process-group signal, and a monitor exception with short Python children; they do not establish complete descendant containment or actual Lean behavior. Any production use requiring a strict complete-drain guarantee needs a stronger containment mechanism or explicit assumptions, and should not infer such a guarantee from these controls.
