# Coherent source replay of the PA194 startup

This supplementary replay rebuilds the machine-specific dependency closure in
one new output directory. It avoids combining previously compiled PA194
stepper, table, source-program, or parent-startup objects from separate
overlays. This matters because Lean imports compiled modules as trusted
artifacts and a prebuilt dependent object alone does not authenticate the
transitive definitions it was compiled against.

The script derives two temporary stages from checked-in source checkers:
`pa194-work/pa194-startup/check.sh` (one initial parent checkpoint, together
with the entire generated parent seed definition) and
`pa194/ipra/machine-code/check-stepper-zip.sh`. It changes only their temporary
output location, repository discovery and cleanup so both write into one fresh
private directory. It then rebuilds the finite-control, equality-transfer,
standard-code and model bridge modules there, regenerates the 46 dense batch
modules, checks all 455 blocks, composes them and checks the model and native
iPRA startup sentences. It rejects any `sorryAx` in printed theorem axioms.

The checker rejects Lean search roots containing PA194/195/196, M6, PA196,
or known standalone machine implementation objects, so the machine-specific
objects must come from its common build directory. It retains the existing
`IPRA_LEAN_OVERLAY` for the general primitive-recursive/iPRA development and
`IPRA_FOUNDATION_OVERLAY` for Foundation, together with the project's Mathlib
objects. Those foundational imported objects are not rebuilt by this script;
the existing source checkers pin selected direct dependencies, not the entire
transitive foundational closure.

The tested roots were `/tmp/current14-standard-fresh-build-20261104/lib` and
`/tmp/ipra-foundation-guarded-v2-cjHUaJun/package-lib`, plus the 11 ordinary
`lake env printenv LEAN_PATH` roots. All 13 non-task roots were checked for
the rejected machine-specific objects/directories. No prebuilt PA194 machine
overlay was used. A short run with `PA194_AUDIT_BLOCK_GROUPS=1` rebuilds the
machine and generic bridge sources and checks only the first dense batch; it
explicitly does not establish the full startup theorem.

The exact 58,154-step literal run and its native iPRA equality are finite
startup facts. They do not establish an arbitrary-length source-controller
simulation or either implication relating literal halting to `Con(PA)`.

A completed audit used `/dev/shm/pa194-standalone-replay/build` as its shared
output. First, the generated `parent.sh` ran with `--start-block 0
--stop-block 1`; next, the generated `stepper.sh` ran with the two overlays
above; finally `run_remaining.sh` ran with `PA194_AUDIT_BLOCK_GROUPS=46` in
that same directory. Logs are `/tmp/pa194-standalone-parent.log`,
`/tmp/pa194-standalone-stepper.log`, and `/tmp/pa194-standalone-full.log`.
All three stages exited successfully. The full log records all 46 dense batch
groups and the final four reported statements. None of those logs contains
`sorryAx`. `startup_exact` printed `[propext]`; `modelDenseStartup`,
`modelSentence`, `classicalPRA`, and `nativeIPRA` printed
`[propext, Classical.choice, Quot.sound]`.

The staged checker preparation was generated by
`/dev/shm/pa194-standalone-replay/prepare.py`; a separate check confirmed that
the standalone wrapper's embedded preparation generates byte-identical
parent and stepper stages. A separate full invocation of the installed
wrapper then completed successfully, rebuilding the machine-specific closure,
all dense blocks and the final native-iPRA sentence without `sorryAx` in the
reported dependencies. Its log is `/tmp/pa194-coherent-wrapper.log`.
