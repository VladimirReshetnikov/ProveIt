# Proof simplification research: portable release

21 October 2026. This is a research and finite-checking packet, **not a newly kernel-verified Lean or Rocq endpoint**. It contains no established 214-state construction.

Start with `report/report.pdf` (and its editable `report/report.tex`), then `review/REVIEW.md`. The detailed technical sections are `rocq/CFG_REPORT.md`, `lean/profiling/README.md`, `runtime/REPORT.md`, `transport/README.md`, `candidates/COMPARISON.md`, `enumeration/LENGTH_PADDING.md`, and `new_intake/gc_zc215/ASSESSMENT.md`.

## What is established at which level

1. **Published historical kernel evidence, not rerun here.** The accepted original 215-state machine has existing Lean and Rocq correctness endpoints. Its original Rocq closure records 237 sources, four closed assumption reports, and a recursive endpoint check. Later published simplifications use explicitly distinguished incremental/hash-bound evidence. Historical build receipts and timings are not new builds or forecasts.
2. **New independently replayable finite results.** The two source programs have equal 1,426-node increment-count block CFGs. Their ordered 3,326-primitive CFGs differ by 256 adjacent independent-increment swaps generated by two shared DAG templates. Reversing just those two templates makes the ordered CFGs equal. Canonicalization removes 814 aliases from 2,240 checkpoint rows; further exact labeled-bisimulation minimization removes only three more rows. The packet also replays certificate data, CM215 local transport obligations, exact runtime lookup comparisons, candidate interfaces, and bounded local-window certificates.
3. **Ordinary mathematical arguments and design proposals.** Generic canonical-checker soundness, source/CFG correspondence, whole-tape locality, positive stuttering, and the enumerator length-bound abstraction are explained, with remaining hypotheses explicit. They are not supplied by a Python PASS or a graph hash.
4. **Formal drafts are uncompiled.** All newly proposed `.lean`, `.v`, and `.patch` drafts are uncompiled, including the packed certificate and Lean symmetry/canonical-row/local-swap/runtime adapters. Upstream source snapshots are historical reference material, not new drafts. No new compiler or kernel execution is claimed.

Already-upstream rho8/AX/checker simplifications are identified in the reports and are not claimed as new contributions. `latest_targeted_freshness.json` records only three targeted file checks at its later commit, not equality of an entire repository tree. Earlier source/status pins retain their own dates and scopes.

## Candidate conclusion and boundary

CM215 is the shortest proposed incremental proof route from the already verified original, because its source is unchanged and its finite local rewrite has a small invariant. It does not automatically shorten the inherited proof closure. GC-ZC215 supplies an interesting zero-debt proof architecture, but its new scheduler/compiler obligations remain separate from the original endpoint. The bounded window search found no safe state elimination or exact state merger. None of these results establishes a calibrated 214-state machine.

## Portable replay

Requires Python 3.10 or later with its standard library. The release was tested with the version recorded in `REPLAY_RECEIPT.json`. No network, Git checkout, package installation, Lean, Rocq, C++ compiler, or TeX is required for the finite replay.

Run from any working directory:

    python3 -B /path/to/research_proof_simplification_release/verify_release.py

For package integrity only:

    python3 -B /path/to/research_proof_simplification_release/verify_release.py --hash-only

To include the packaged mutation/optimization rejection suites:

    python3 -B /path/to/research_proof_simplification_release/verify_release.py --negative-controls

The outer verifier rejects `-O`, `-OO`, and any `PYTHONOPTIMIZE` setting, verifies the pinned manifest and every packaged payload byte, then copies the packet to a temporary directory. Writing checkers run only in that copy. Recomputed principal outputs are compared with the archived outputs. The original release is rechecked afterward. The verifier creates no files in the release; direct checker invocation may write adjacent outputs, so use the outer verifier.

The manifest intentionally excludes only itself and `verify_release.py`. The verifier embeds the exact manifest digest. Authenticate the whole ZIP against the separately delivered release SHA-256 before trusting the verifier; an internal hash is not a signature or proof of provenance. Any modified payload or unlisted file fails closed. Do not place redirected output inside the release directory.

`REPLAY_RECEIPT.json` records the completed 17-check replay against the exact `REPLAY_INPUT_MANIFEST.json`, before report/review and release bookkeeping were added. All executed checker/input payloads remain unchanged; the final manifest also binds those later documents. The verifier’s embedded manifest constant is updated for final packaging. The receipt is evidence, not a substitute for rerunning. `OUTER_NEGATIVE_CONTROLS.json` records 11 isolation/tampering/optimization checks; reproduce them with `python3 -B tests/test_outer_verifier.py`. Python durations are diagnostics, not proof-assistant speedups. `PORTABILITY.md` describes dependencies and evidence-only programs.

## Safety and scope

The outer verifier has an explicit allowlist of independently written research checkers. It never runs historical snapshot generators, incoming archive members, upstream build scripts, report TeX, or received proof code. `new_intake/gc_zc215/received.zip` is retained only as exact hash-pinned input data for the owned read-only audit; that audit reads members with `zipfile` but never imports or executes them. The source archive includes untrusted code and uncompiled drafts, which remain data.

Compiled executable binaries, Python caches, active `credit_encoding`/`gc_backend` experiments, and irrelevant local transient logs are omitted. Binary window bitsets and the incoming source ZIP are intentional data certificates/inputs, not executable binaries. Selected historical receipts/logs are retained as evidence. `STAGING_SELECTION.json` describes omissions.

The TeX report can optionally be rebuilt with a conventional TeX Live installation using `report/build.sh`. This is outside the finite replay and was not part of its trust boundary. Pinned historical sources are not a complete buildable proof-assistant distribution.
