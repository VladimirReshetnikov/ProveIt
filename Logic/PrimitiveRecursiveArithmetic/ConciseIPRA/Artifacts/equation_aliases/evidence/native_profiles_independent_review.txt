3. WHOLE-ALPHABET GATE

The gate is:
  p = json.load(open(0))
  q = not str(p).strip('0123456789-[], ') and p.pop

Every finite JSON value is a tree over lists, dictionaries, exact Python
ints, floats, bools, strings, and None. The repr of any non-int/list value
contains a character outside this alphabet: quotes, braces, a decimal dot,
or letters, including nan/inf/True/False/None. Exact integer/list trees have
only the listed characters. Thus a successful gate permits precisely the
int/list alphabet. If a top-level integer passes the alphabet test, p.pop
fails; so successful operation also requires a list. No external Python
object with a malicious repr is possible through the JSON input interface.

If the alphabet test fails q becomes False, and the mandatory q() call
rejects before entering the checker. Unsupported top-level objects similarly
reject. The public-goal scanner remains mandatory in every profile.

Only two changes distinguish the 642-byte candidate from this matched
strict control:

(i) Remove 'int(a) is a' from the initial public grammar scanner. At every
initial successful scan, the gate has already established exact integer
leaves. On an exact Python int, int(a) returns the same object in the fixed
CPython runtime, so the test is true. In all subsequent checker phases the
context g is nonempty, and the preceding 'g or ...' bypasses the test even
in the old code. Invalid array-shaped objects fail an earlier comparison,
and the function sentinel fails its earlier multiplication/comparison; the
removed test does not create an acceptance route for either. Runtime-derived
Boolean neutral values occur only after the phase becomes nonempty, so they
are not a counterexample to the root exact-int argument.

(ii) Replace '(i := lambda ...) and (i(a) in g or ...)' by immediate
application '(i := lambda ...)(a) in g or ...'. A newly constructed lambda
is truthy. The assignment still occurs before the mandatory first i(a)

and subsequent body are unchanged. Evaluation order is identical.

5. THE 633-BYTE PROFILE

This differs from the incoming strict637 source ONLY by:
  v <= (d % 2 and (not a or a > 1 == a % 2))
becoming
  v <= d % 2 * (not a or a > 1 == a % 2).

The whole-alphabet gate makes external leaves exact integers. Internal
numeric leaves are integers/Boolean neutral values; nonnumeric arrays or
the function sentinel encounter an earlier type-incompatible multiplication
or k<=a<d comparison. Therefore, whenever this predicate is reached in a
successful run, its arithmetic/comparison expression is total and pure.

Let e=d mod 2 and P=(not a or (a>1 and 1=a mod 2)). Both are Boolean bits.
The old subexpression is 0 when e=0 and the Boolean P when e=1. The new one
is the numerically equal integer e*P. Comparing either with the internal
numeric phase flag v gives the same result. The only change in evaluation
is that P is computed when e=0; its totality and absence of effects make
this harmless. Scope k, depth d, the predicate's result, and every later
proof operation remain unchanged.

Replacing this one product spelling back by the original conjunction gives
the exact complete AST of the pinned strict637 module. The profile therefore
preserves its exact finite successful acceptance relation on JSON inputs,
apart from physical resource limits common to this framework.

9. FINAL PRODUCT / BIT-OR / FRAMING COMPOSITION AUDIT

The final token profile composes the g-phase product rewrite with replacement
of the scanner fallback flag
  (d % 2 or not g)
by
  d % 2 | (not g).
The final AST profile additionally applies the already-reviewed module-level
framing rewrite. Exact AST inversion of both arithmetic spellings reproduces
the audited 642-byte candidate; unwinding the final AST profile's framing
gives the exact AST of the final token profile. See
review/native_final_composition_ast.json.

The fallback flags are truth-equivalent because d%2 and not g are bits.
Evaluating not g when the old 'or' skipped it is harmless: g is an actual
finite list, so its truth test is total and effect-free. When the fallback
condition is false, the old complete 'flag and i(...)' expression can return
Boolean False whereas the new one returns integer 0. This is not literal
Python-type identity. It is a safe observational equivalence of neutral
scalar values, which needs to be stated rather than concealed.

Relate runtime trees by replacing Boolean False leaves by integer 0, with
all other integer leaves, list structure, contexts, packet positions and
scope floors equal. The only introduced difference is exactly this neutral
leaf replacement. Every subsequent data operation in these kernels respects
the relation: truth tests agree, scalar arithmetic agrees, list structural
and tuple equality use Python numeric equality (False == 0), list membership
agrees, and scanner dispatch a*0 !=0 agrees. Noniterable unpacking and len
errors on either neutral scalar reject in both versions. The removed exact
int-identity test is absent, and no remaining type/identity test distinguishes
these internal neutral values. The lexical str(p) gate runs on the original
parsed input before any runtime neutral value is generated, so that gate is
not affected. Thus all successful scanner results are related, all proof
branch decisions agree, and major/continuation packet consumption and scope
operations agree. Induction on finite successful evaluation trees transfers
acceptance in both directions. Physical resource-limit identity is not claimed.

The public validation scan initially runs with g empty, so its fallback
flag is true in both versions. Invalid public numerical leaves still invoke
the same failing function sentinel; no previously invalid public syntax is
made valid by the False/0 equivalence. After validation, the context is
nonempty and remains so. The change therefore does not weaken the public
grammar, freshness, scope, or whole-input alphabet obligations.
